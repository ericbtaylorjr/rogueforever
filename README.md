# Rogue DPS Handbook

Single-page reference site for World of Warcraft Forever Rogues. Built from the
Claude Design handoff package (`design_handoff_rogue_compendium`).

React 19 + Vite 8 + TypeScript + Tailwind CSS 4.3, deployed to GitHub Pages.

```bash
npm install
npm run dev        # http://localhost:5173
npm run build      # tsc -b && vite build -> dist/
npm run typecheck
```

## Structure

```
src/
  config.ts                  build config (navLayout, simView, intensity, accent, …)
  styles/index.css           design tokens (@theme inline), type roles, keyframes
  content/
    content.json             data, verbatim from the handoff — edit this, not markup
    content.ts               typed loader + derived filters/counts
    copy.ts                  prose extracted from the prototype markup
    types.ts                 content types incl. the real GearItem schema
    builds/                  every build, one file per spec: talents, stats, gear, rotation
    gear.ts                  shared leveling milestone lists, item quality + faction colours
    links.ts                 every external URL — all TODO placeholders
    icons.json               name -> Wowhead id + icon (generated by `npm run icons`)
    talent-trees.json        Rogue talent trees from Wowhead's calculator (`npm run talents`)
    searchIndex.ts           ~126-entry command palette index
  state/HandbookProvider.tsx all page state, scroll-spy, keyboard, persistence
  components/shell/          sidebar, mobile bar, drawer, palette, spec bar, top tabs
  components/ui/             droplet, logo, callout, pills, copy button, tooltip
  components/sections/       the 15 sections, one file each
```

## Decisions worth knowing

**Tokens live in CSS variables, not in `@theme` directly.** `:root` holds the raw
values and `@theme inline` maps them into Tailwind's namespace, so `bg-panel`,
`text-mute` and `border-line` all follow a runtime override. That's what makes
the `intensity` / `accent` build config work without a second stylesheet.

**Display type is CSS component classes** (`.t-h1`, `.t-h2`, `.t-card-title`, …)
rather than piles of arbitrary utilities, so the values are easier to tune in one place.

**Typography:** headings use the Literata book serif (`--font-display`) and body text
Source Sans 3 (`--font-sans`), mixed case: a reference book rather than a dashboard. Condensed
uppercase Archivo (`--font-brand`) is reserved for the brand: the hero title, the wordmark
and the raid badges. IBM Plex Mono is only for code and key chips; numbers use the body
face with tabular lining figures (`.t-num`). Keep monospace out of labels.

**Breakpoints are named for what they do**: `stack:` (900px), `hero:` (980px),
`rail:` (1100px), `wide:` (1600px). Layout comes from these CSS breakpoints only, so the
page renders the same before any script runs. The few behaviours that need one in JS
(closing the drawer, scroll offsets) read the same numbers from `src/config.ts`.

**Switching spec or build keeps your place.** The section you're reading stays where it is
on screen while the content above it changes height (`src/lib/keepPlace.ts`).
Nothing scrolls into view or animates.

**Tips use `<Tip>`** (`components/ui/Tip.tsx`), never a hand-styled `<Callout>`. The
colour says who a tip is for: yellow (default) for every Rogue, blue with the droplet
(`sweaty`) for sweaty tips, and the active spec's colour (`spec`) for tips that only
apply to that spec. A `spec` tip can also be `sweaty`. Sweaty tips hide themselves when
sweaty tips are off. `<Callout>` stays for statuses, warnings and Forever claims.

**Copy never lives in JSX.** `content.json` covers every data array; the hero,
section intros, callouts and footer are in `copy.ts` because the prototype
authored them in markup.

## Deliberately unfinished

- **Builds** live in `src/content/builds/<spec>.ts`. The spec bar picks a spec, then one
  of its builds; Talents, Stats, Gear and Rotation all show the active build, and nothing
  falls back to the spec. Builds that agree on something share one constant (each spec
  file's `stats`, for example), so giving one build its own data is a local change.
  Every build carries a `grade` (S–D, or `X` as a placeholder until it's graded) and a
  `rank` (1 = best, across every spec) for Meta breakdown, whose End Game / Leveling toggle
  shows one ranking for level 60 builds and one each for Questing and Dungeons. Builds
  come in two kinds (`phase`): **Level 60** builds carry Pre-raid BiS and Best in Slot gear;
  **Leveling** builds name their `activity` (`questing` or `dungeons`) and carry a
  level-ordered milestone gear list instead. Switching spec keeps you on the same kind
  of build (see `buildForSwitch` in `builds/index.ts`).
- **Gear table** renders 17 slot rows against the real `GearItem` schema and shows
  an empty state. Fill a level 60 build's `gear.prebis`/`gear.bis` and every row fills,
  Wowhead quality colouring, tooltips and icons included. A list with no items shows a
  "Coming soon" note (`gear.comingSoon` in `copy.ts`) instead of an empty table.
- **Leveling milestones** come from `src/content/leveling-gear.json`, generated from
  Wowhead's Forever database by `scripts/gear-research` (see its README for how to rerun
  it as items are decrypted). Hand fixes go in `scripts/gear-research/curation.json`.
- **Empty sections say so in one line** instead of showing placeholder UI. Meta
  Breakdown, Rotation and a build's Talents card each render a short note until
  their data exists (`specIndex`/`levelingIndex`, a build's `rotation`, `talents` and
  `talentNote`); filling the data brings the full layout back with no code change.
- **Game icons** for poisons, consumables, buffs, gear and Expose/Sunder Armor are
  self-hosted in `public/icons/`, resolved by name through Wowhead's Forever search
  (`scripts/fetch-icons.mjs`, run with `npm run icons`). Re-run it after adding
  anything; a name it can't resolve just renders without an icon. Icons are
  Blizzard game art, used as fan-site reference material.
- **Talent trees** in a build's Talents card are drawn from its calculator
  `link` alone: paste a Wowhead Forever talent calculator link
  (`https://www.wowhead.com/forever/talent-calc/rogue/v2…`) into the build and the tree
  follows. `src/lib/talentCalc.ts` decodes it (one digit per talent, row by row, trees
  split by `-`) against `src/content/talent-trees.json`, which `npm run talents`
  (`scripts/fetch-talents.mjs`) builds from Wowhead's calculator data, along with the
  talent icons and tree art in `public/talents/`. That command also checks every build's
  link against the trees; `npm run talents -- --check` does only the check. Re-run it
  when Forever's talents change. A link that doesn't fit the trees falls back to the
  point split bars. Leveling builds also list the link's **talent order** (the part after
  the trees' `/`, Wowhead's "Talent Order"): a digit picks the tree, each letter is one
  talent in it (`abcdefghjkmnpqrstvwxyz`, row then column), lowercase spends one point
  and uppercase fills it to max; `decodeTalentOrder` reads it, from level 10, one point a
  level, and the check makes sure it ends on the link's ranks.
- **Rogue class icon** is a hand-drawn stand-in, isolated in
  `components/ui/RogueMark.tsx`. Swapping it touches one file.
- **External links**: only Comfy's UI is still a placeholder (`weakauras: '#'` in
  `src/content/links.ts`); its card renders as a disabled "Coming Soon" button.
- **Vite `base`** is `/`. For a GitHub Pages project site, set `VITE_BASE` to
  `/<repo-name>/` in `.github/workflows/deploy.yml`.

## Accessibility

Target: WCAG 2.2 AA. Last audited 22 October 2026 with axe-core 4.10 (0 violations at 1440px
and 390px, dark and light, on an endgame build, the Combat and Subtlety leveling builds with
their milestone gear tables, and an open Wowhead tooltip), a 274-stop keyboard walk (every
stop shows a focus ring) and Lighthouse 12 (Accessibility 100). Earlier audits also covered
the palette, drawer, profile modal and an open raid.

Covered: skip link and `<main>` landmark; nav jumps and shared section links
(`?spec=combat&build=backstab#talents`, scrolled to once the page has loaded) move keyboard
focus to the target section and respect `prefers-reduced-motion`; tabs use roving tabindex with
arrow/Home/End keys; the palette is a real combobox/listbox with a live result count;
tooltips are dismissible (Esc), persistent while their trigger is hovered or focused, and only
set `aria-describedby` while showing; focus is kept clear of the sticky bars (`scroll-padding-top`); the Gear
table has table semantics and its scroll region is keyboard-reachable; copy buttons have
unique names and announce success; no bare-key shortcuts (WCAG 2.1.4 — only Ctrl/⌘+K);
text meets 4.5:1 (`--dim` is deliberately light — don't darken it back). Content colours go
through `useTheme().tone()` in both themes: on parchment it darkens them, on dark it lightens
the few that fall short (WoW's rare blue and epic purple), so item names always clear 4.5:1.

Talent trees (`ui/TalentTree.tsx`): one tab stop per tree, arrow keys move between talents
(up/down to the nearest talent in the next row, Home/End); each talent is a link to its
Wowhead page at the build's rank (new tab), reads as "Malice, 5 of 5", and its tooltip starts with the rank text from `talent-trees.json`, so screen readers hear
the description on focus before Wowhead's live tooltip loads. The card title is an `h3` and
each tree an `h4` with its points. A leveling build's talent order is an `ol` with one tab
stop (arrow keys, Home/End); each line is the same kind of link and tooltip, read as
"Levels 14 to 16: Lightning Reflexes, 3 of 5, Combat". The window stays dark in both themes, so its focus ring is
white rather than the accent (the light theme's dark red would be ~1.8:1 there). In Windows
High Contrast, maxed talents get a solid frame, partly ranked a dashed one, untaken grey.
Maxed vs partly ranked is otherwise shown by frame colour (gold/green) as in-game; the rank
and maximum are in each talent's name and tooltip.

Known / accepted: the hero's looping poison drips have no pause control beyond
`prefers-reduced-motion` (WCAG 2.2.2). Tooltips are deliberately **not hoverable** (WCAG
1.4.13): moving the pointer off the trigger hides them, so the next item in a list shows its
own tooltip instead of being covered. Their content is display only, and every item and spell
with a tooltip also links to its Wowhead page. Not done yet:
arrow-key navigation between raid accordion headers (not required by WCAG).

## Performance

Last measured 22 October 2026 with Lighthouse 12 against the production build: desktop
Performance 100 (LCP 0.7s, CLS 0), throttled mobile 97 (LCP 2.4s, TBT ≤60ms), about
355 KiB transferred. Under the same throttling in Chrome itself (4× CPU, 1.6 Mbps), mobile
LCP is ~1.8s: the intro paragraph, painted once the JS bundle (135 KB gzipped, most of it
React DOM) has downloaded and rendered. Keep it that way:

- **Size images for their display size.** Images are WebP at about 3× their CSS size
  (crisp on high-density phones). Don't ship source art; `sharp` is a dev dependency
  for resizing.
- **Game icons** load lazily from `public/icons/` (~1–3 KB each).
- **Wowhead tooltip data** loads only when a tooltip first opens, one small JSON request per
  item, cached for the page's life (`src/lib/wowhead.ts`).
- **The theme script is inlined** at build (see Security), so first paint waits only on the
  one small stylesheet.
- **First-screen fonts are preloaded** (Archivo for the hero, Source Sans 3 for the
  intro) by the `preload-fonts` plugin in `vite.config.ts`. Update `PRELOAD_FONTS` if the
  hero's fonts change. On a slow connection they share bandwidth with the JS bundle, so
  keep them small.
- **Archivo and Literata are instanced** to the axis ranges the site uses (Archivo 90 →
  22 KB, Literata 86 → 56 KB; see `src/assets/fonts/LICENSE.md`). A new weight or width
  outside those ranges needs the fonts re-instanced from the Google Fonts files, and the
  `@font-face` ranges in `styles/index.css` updated.
- **Repeat visits load from a service worker** (`src/sw.js`, written to `dist/sw.js` with
  the build's file lists by the `service-worker` plugin in `vite.config.ts`). GitHub Pages
  serves everything with a 10-minute `max-age`, so without it a returning visitor
  re-checks every script, font and icon with the server first. The page is network-first
  (a deploy shows on the next load; the last copy opens offline), hashed `/assets/` are
  cache-first, and other site files are served from the cache and refreshed behind it.
  Each deploy's worker prunes files the build no longer has. Cross-origin requests
  (Wowhead, analytics) aren't touched. **To switch it off**, replace `src/sw.js` with one
  that calls `self.registration.unregister()` on activate and deploy it; removing
  the file alone leaves installed workers running.
- **A build pick paints the lists first.** Picking a build re-renders the Talents card and
  the Stats, Gear and Rotation sections, which on a slow phone took ~200–330ms before the
  click painted (Cloudflare INP). They read the build through `useShownBuild()`
  (`useDeferredValue`), so the click paints the button state at once and the rest
  follows in an interruptible render (~100ms worst case at 10× CPU). Anything new that
  follows the build and sits below the lists should use it too.
- **Talent tree backgrounds are re-encoded** (mozjpeg, progressive, ~24 → ~11 KB each) by
  `npm run talents` when it downloads them.
- **Cloudflare's analytics beacon loads at `fetchpriority="low"`**, so it doesn't compete
  with the app's own JS. Its "legacy JavaScript" and short cache Lighthouse notes are
  Cloudflare's, not ours.
- The remaining Lighthouse notes (unused JS in the single bundle; ~1,450 DOM nodes, ~2,150
  on a leveling build with its three milestone gear tables) are
  expected for a one-page app this size.
- **Not done, on purpose:** `content-visibility: auto` on later sections saves ~100ms of
  mobile LCP but makes section positions estimates, which breaks deep-link scrolling and
  keeping your place on a build switch. Pre-rendering the HTML at build would paint the
  hero without waiting for JS. Layout and theme no longer depend on script (CSS
  breakpoints, `theme-init.js`) and the app renders on the server, but the URL's and
  remembered build would still swap in after load unless the default build is the
  only one prerendered. Swapping React for Preact (`preact/compat`)
  would cut ~50 KB gzipped from the bundle; it's the cheapest remaining win, but needs a
  full regression pass.

## Theming

Dark is the default; light is a papyrus "bounty letter". Which one you get: a choice made
with the sidebar toggle (`localStorage['rc:theme']`) → the device's `prefers-color-scheme`
(followed live until the toggle is used) → dark. `src/theme-init.js` (inlined into `index.html` at build, allowed by its CSP hash) resolves this before
first paint (no flash) and `src/state/ThemeProvider.tsx` owns it afterwards; both write
`data-theme` on `<html>`. Note browsers report "light" for a device with *no* preference, so
"unset" can't be told apart from "light" — that's a platform limit, not a bug.

- **Tokens, not hex.** Every colour comes from a CSS variable defined twice in
  `styles/index.css` (`:root` = dark, `:root[data-theme="light"]` = light). Tints are
  `rgba(var(--accent-rgb), .1)` so they follow the theme. Don't hardcode colours in JSX.
- **Content colours** (spec hues, poison hues, item quality) are authored for dark. Text or
  bars that use them go through `useTheme().tone(hex)`, which darkens a colour just enough to
  stay legible on parchment (identity in dark).
- **Light contrast is measured against the worst paper pixel (`#cbb386`), not `--bg`.** The
  grain and vignette darken the page by ~15%; text on bare paper must still clear 4.5:1
  there. Change the texture, vignette or `--bg` and you must re-measure (render, sample the
  darkest bare-paper pixels, check the text tokens).
- `config.intensity` / `config.accent` only tune the dark theme (`lib/theme.ts`).

## Security

Static site, no backend, no user input beyond a search box, no third-party scripts beyond
analytics (below). `npm audit` is clean.

- **Wowhead tooltips:** item and spell tooltips fetch JSON from `nether.wowhead.com`
  (Forever data only) the first time each one opens, so the CSP
  allows that host in `connect-src` only. Wowhead's tooltip HTML is the one use of
  `dangerouslySetInnerHTML`: `src/lib/wowhead.ts` rebuilds it through a tag allowlist,
  turns links into plain text, keeps only `class` attributes, and drops everything else.
  The tooltip is display only (`pointer-events: none`); clicking the item itself opens Wowhead.
  Talent tooltips use the same API with the talent's `def` and `rank`, as Wowhead's
  calculator does; talent icons and tree art are self-hosted.

- **Visit counts:** Cloudflare Web Analytics runs for every visitor once `cfBeaconToken` in
  `src/config.ts` holds the site token. It's cookieless and stores nothing on the device, so
  it isn't behind the consent banner. The `cloudflare-web-analytics` plugin in
  `vite.config.ts` adds the script tag at build (never in dev) and its hosts to the CSP. It
  reports totals only: visits, page views, referrers, countries, devices, page speed. Read
  them in Cloudflare → Analytics & Logs → Web Analytics.

- **Analytics:** Google Analytics 4 runs only when `analyticsId` in `src/config.ts` holds a
  `G-…` measurement ID, only in production builds, and only after the visitor allows it on
  the consent banner (`ConsentBanner.tsx`). Until then nothing from Google loads. Declining
  or a Global Privacy Control signal keeps it off; the choice (`localStorage['rc:consent']`)
  lasts 12 months, can be changed from the footer's "Cookie settings", and withdrawing it
  clears GA's cookies. Ad storage and ad signals are always denied. `src/lib/analytics.ts`
  loads gtag.js (no inline snippet), and the build adds Google's hosts to the CSP only while
  an ID is set. Events and how to read them: see Analytics below.
- **Privacy policy** lives in `copy.ts` (`privacy`) and opens in a dialog from the footer, the
  consent banner, or a `#privacy` link. It describes the code as it stands (storage keys, GA
  events and cookies, hosting), so update it, and its `updated` date, whenever those change.
- **Fan-project disclaimer:** the footer's bottom bar states the Handbook has no affiliation
  with Blizzard Entertainment, plus the standard trademark line. Keep both.

- **CSP** ships as a `<meta>` tag injected at build time (`vite.config.ts`); everything is
  first-party, including fonts (`src/assets/fonts`, OFL) and game icons. `style-src` needs
  `'unsafe-inline'` for the design's inline styles; `script-src` does not. The one inline
  script (the pre-paint theme script) is allowed by its exact SHA-256 hash, computed from
  `src/theme-init.js` at build, so any other inline script is still refused.
- **Limits of GitHub Pages:** it can't set response headers, so `frame-ancestors`
  (clickjacking), HSTS and `X-Content-Type-Options` aren't available. If the site moves
  behind Cloudflare/Netlify, set them there.
- **External links** use `target="_blank"` with `rel="noreferrer"` (implies `noopener`).
- **Stored data:** the spec and build are always in the URL (`?spec=&build=`) and also saved
  to localStorage so returning visitors land on their last build. Resolution order: URL →
  last saved → Combat's best-ranked build. The spec is validated against the known spec list
  (`assassination`, `combat`, `subtlety`; the old `mutilate`, `sinister`, `backstab` ids are
  mapped to them) and the build against that spec's builds; anything else is ignored.
- **CI:** actions are pinned to commit SHAs, the workflow defaults to read-only, and only
  the deploy job gets `pages`/`id-token` write. Dependabot keeps both up to date.

## Analytics

Every event goes through `track()` in `src/lib/analytics.ts`, which sends nothing without
consent and nothing outside production. In `npm run dev`, after you click "Allow analytics",
events print to the browser console as `[analytics] <event> {…}` instead, so new tracking can
be checked without polluting the numbers.

Every event also carries `active_spec`, `active_build` and `sweaty_mode`, so anything can be
split by spec or build.

| Event | Fires when | Parameters |
| --- | --- | --- |
| `section_view` | a section has been on screen for 2s or more (sent when it leaves view, the tab is hidden, or the page closes) | `section`, `seconds`, `via` (`nav`/`scroll`), `nth_section` |
| `section_jump` | a section is opened from the nav, search or an in-page link | `section` |
| `spec_select` | a spec is picked | `spec` |
| `build_select` | a build is picked | `spec`, `build` |
| `sweaty_toggle` | sweaty mode is switched | `enabled` |
| `gear_tab` | a Gear tab is picked | `tab` |
| `meta_tab` | Meta breakdown switches between End Game and Leveling | `tab` (`endgame`/`leveling`) |
| `filter_select` | a Consumables or New to Rogue? filter is picked | `list`, `filter` |
| `raid_open` | a raid entry is expanded | `raid` |
| `tooltip_view` | a tooltip stays up 0.7s | `name`, `kind` |
| `search_open` | search opens, by any route | — |
| `search` | search closes after a term was typed | `search_term`, `results`, `picked`, `position` |
| `copy` | a macro (or other copy button) is copied | `item` |
| `theme_toggle` | light/dark is switched | `theme` |
| `comfy_preview_open` / `comfy_profile_open` | the Comfy's UI preview or an import string opens | — / `profile` |
| `sim_set` / `table_sort` | the sim table changes set or sort | `set` / `column` |

`section_view` measures what is actually read: a section counts while it fills at least half
the screen (or half of it shows, if it's shorter than that). Returning to a section counts
again, so its event count is views. Logic lives in `src/lib/sectionViews.ts`.

**GA setup (one time).** GA ignores custom parameters until they're registered, and never
backfills, so do this before you rely on the data.

1. **Admin → Custom definitions → Create custom dimension**, scope *Event*, one per
   parameter, with the parameter name as the dimension name: `section`, `via`,
   `nth_section`, `active_spec`, `active_build`, `sweaty_mode`, `spec`, `build`, `enabled`, `tab`, `list`,
   `filter`, `raid`, `question`, `name`, `kind`, `picked`, `item`, `theme`, `profile`, `set`,
   `column`. (`search_term` is built in.)
2. **Custom metrics**, scope *Event*: `seconds` (unit: Seconds), `results` and `position`
   (unit: Standard).
3. **Admin → Data streams → your stream → Enhanced measurement**: keep page views and
   outbound clicks on. Turn **Site search off**: the Handbook sends its own `search` event,
   and GA's would look for a URL query that never exists here.

**Reading it** (Explore → blank exploration):

- **What gets read:** Free form. Rows `section`, values *Event count* and *Average seconds*
  (or `seconds` ÷ event count), filter *Event name = section_view*. Add `active_spec` as a
  column to compare specs, or `via` to see what's found by scrolling versus the nav.
- **Reading order:** Free form with rows `nth_section` then `section`, filtered to
  `section_view`: which section is usually read first, second, and so on. (Path exploration
  only shows event names, not their parameters, so it's better for the order of actions,
  e.g. `spec_select` → `build_select` → `copy`.)
- **How far people get:** Funnel exploration, open funnel, steps `section_view` where
  `section` = `overview` → `talents` → `stats` → `gear` → `rotation`.
- **What people click:** Free form, rows *Event name*, then drill into `filter`, `raid`,
  `question` or `name` (tooltips).
- **What people look for:** Reports → Engagement → Events → `search`, or a free form on
  `search_term` with `results` (zero results = missing content) and `picked`.

## Editorial rules the code enforces

- New to Rogue? entries that relay a Blizzard change link their official `sources`
  (news.blizzard.com, worldofwarcraft.blizzard.com, blue posts). Plain tips leave `sources` empty.
- The spec board is a 0–100 consensus index, never simulated DPS.
- The sweaty marker is a CSS teardrop, never an emoji.
